# Правила работы с NEXTGENONE

UE 5.9.0, C++, движок `E:\UE_5.9`.

## Порядок работы

- Брать одну ограниченную задачу с наблюдаемым результатом. До существенных правок назвать затрагиваемые системы и способ проверки. Сначала искать причину в существующем коде.
- Сохранять изменения пользователя. Не совмещать исправление с посторонним рефакторингом, массовым переносом или импортом стороннего framework. Новые подсистемы и адаптеры вводить только при конкретной потребности. Новые идеи предлагать отдельно.
- Агент отвечает за C++, GAS и сетевую логику. Blueprint, UMG, визуал и анимации обычно настраивает пользователь. Указывать точные классы, поля и события. Редактировать ассеты, когда это входит в поручение.
- Кратко сообщать, что изменено, что фактически проверено и какие действия требуются от пользователя. Компиляция и сохранение ассета не подтверждают поведение в игре.
- Создавать и обновлять документацию только по явной просьбе. Детали реализации, миграций и проверок хранить в профильной документации или PR.

## Сборка и проверка

- Для сборки и запуска использовать `StartEditorFast.cmd` из корня проекта. При запуске из IDE передавать тот же аргумент `-DDC`, что в скрипте.
- **Сборку выполняет пользователь. UBT и Live Coding запускать только по отдельному запросу.**
- **Автотесты, PIE, smoke/regression, сетевые прогоны, latency и packet loss требуют отдельного явного согласования.** Обычное чтение кода и diff входит в работу.
- Если нужен закрытый редактор, согласовать одно окно на весь пакет. Не закрывать и не перезапускать редактор самостоятельно. Длительные командлеты, серверы и очистку проекта запускать при необходимости и после согласования.
- Для разрешённой сборки использовать `ue-build`, для редактора `ue`, для логов `ue-logs`. Основывать выводы на фактических результатах.

## Код, инструменты и Git

- Не добавлять комментарии в код без явной просьбы. Не использовать `friend`. Открывать узкий API владельца вместо доступа к его полям.
- Имена локальных переменных и параметров не должны скрывать члены класса или его базовых классов. Выбирать имена по назначению.
- Каждая проверка защищает конкретное обращение или инвариант. Перед удалением проверки сверять контракт вызываемого API. Сохранять проверки разыменований, жизненного цикла и недоверенных сетевых данных. Обрабатывать результат операции.
- Runtime API по умолчанию C++. Blueprint API добавлять при конкретной потребности. Сохранять reflection для GC, сериализации, RPC, RepNotify, callback и редакторских настроек.
- Редакторские поля нового класса выводить выше унаследованных через `UCLASS(PrioritizeCategories = (...))`. Для порядка внутри категории использовать `DisplayPriority`.
- Настройки и ссылки на контент хранить в существующих definition/config assets. Не добавлять жёсткие `/Game`-пути в runtime. Одноразовые миграции отделять от игрового кода.
- Начинать анализ с локальных файлов и CLI. MCP применять адресно, переиспользовать схемы. Причины тормозов подтверждать замерами. Исторические документы сверять с текущим кодом.
- Сохранять Core Redirects до миграции и проверки ссылок. Для переноса native типов между модулями использовать `ue-core-redirect-migration`.
- Проверять текущую ветку. Коммиты, push и PR делать по текущему запросу пользователя. Бинарные ассеты хранить в Git LFS. Не выполнять `reset`, `clean` и массовое пересохранение ассетов без явной необходимости.
