# Консолидация Player Foundation

Дата: 2026-11-02. Статус: порядок уточнён обсуждением; начат отдельный пакет конфигураций ввода. Последние решения и граница первого пакета — в [CharacterInputSetup.md](../Gameplay/CharacterInputSetup.md).

## Уточнённый порядок

По отдельному поручению пользователя общий модуль уже выделен перед миграцией runtime input: [GameplayFoundationModule.md](GameplayFoundationModule.md). Изменение порядка не расширяет этот пакет до FSM или нового gameplay.

Сначала Input/config, затем FSM персонажа и смерть; модульный перенос после стабилизации. Приведённые ниже номера пакетов сохраняют исходную декомпозицию, но не задают актуальный порядок исполнения. CharacterDefinition заменяет название PawnData. UI и персонаж имеют отдельные FSM на GCFSM/HFSM: UI локальна и не зависит от наличия Pawn; FSM персонажа принадлежит Pawn, его смерть должна сохраняться после UnPossess и смены ASC Avatar. ASC остаётся на PlayerState. Инвентарь блокирует весь Gameplay-ввод. Новые состояния могут временно подключать способности, снимаемые эффекты и IMC с учётом владельца/handles. Это ещё не реализовано первым пакетом конфигураций.

## Основание

Локально просмотрены NextgenonePlayerController, Character, PlayerState, NGAbilitySystem, InventoryStateComponent, PlayerInputSubsystem и базовый ALSPlayerController. В R5 прочитаны ActorTracker и GameInitializationTracker: полезен принцип немедленного выполнения либо ожидания готовности согласованного набора акторов. Код и зависимости R5 не переносим.

Обнаружено:

- Controller создаёт Input Actions и клавиши в runtime, маршрутизирует способности, управляет автоогнём, экипировкой, UI, drop RPC и тестовыми командами.
- PlayerState сочетает Ability Set, отдельный JumpAbility и жёстко заданную выдачу остальных способностей. ASC отдельно обрабатывает конкретный тег взаимодействия.
- Повторная инициализация идёт из нескольких lifecycle callbacks. Защиты старого Pawn уже есть: при рефакторинге они обязательны.
- Aim, UI, damage/projectile и способности используют конкретный Character, хотя части потребителей достаточно Pawn, Character, ASC или компонента.
- InventoryUIRequested в Controller означает запрос открытия UI, а не завершение загрузки инвентаря. OnInventoryChanged означает изменение содержимого. Их нельзя механически заменить одним Ready-событием.
- Родитель ALSPlayerController сам связывает locomotion input и очищает bindings в SetupInputComponent. Порядок подключения новых bindings необходимо сохранить; оригинальный плагин не изменяем.

## Целевой контракт

Controller сохраняет управление игроком, камерой и минимальные lifecycle hooks. В нём нет отдельных обработчиков персонажных действий, клавиш, таймера автоогня и выдачи способностей. UI-состоянием владеет существующий UI/FSM слой.

Pawn получает GameplayInputComponent и одну InputConfig: список Mapping Contexts с приоритетами, соответствия InputAction → GameplayTag и категории маршрутизации (GAS, команды существующих компонентов, локальный UI). Mapping Context определяет клавиши, InputConfig — смысл действий. Одного стандартного IMC недостаточно для произвольных GAS bindings. Новые способности подключаются ассетами без добавления метода в Controller.

Не заменяем ALS locomotion input в этом проходе. Jump/Aim имеют единственный явно заданный маршрут через существующий ALS adapter; двойные bindings запрещены. UI использует существующий PlayerInputSubsystem. При закрытии input, снятии possession, смерти или смене config отправляются releases, очищается удержание и снимаются только собственные contexts/bindings.

Ability Set остаётся единственным источником стартовой выдачи. WeaponDefinition/экипировка сохраняют свои Ability Sets и handles. InputConfig не выдаёт способности и не даёт клиенту серверных полномочий. Hold/автоогонь принадлежит способности либо CombatComponent; серверный limiter остаётся у текущего устойчивого владельца и не сбрасывается при переактивации/equip.

## Готовность игрока

Один небольшой WorldSubsystem хранит локальные player contexts и подписки. Контекст содержит слабые ссылки на APlayerState, AController/APawn и ASC, поколение текущего Avatar и доступные возможности. Сервис координирует зависимости, но не владеет игровым состоянием и не выдаёт способности.

- Отдельные условия: согласованные actors, GAS Owner/Avatar initialized, локальный input готов, inventory доступен владельцу. Потребитель запрашивает только нужные условия.
- На сервере и owning client проверяются связи Controller ↔ PlayerState ↔ Pawn. Simulated proxy не ожидает чужой PlayerController; dedicated server не ожидает LocalPlayer/UI/input.
- Подписка немедленно получает текущее состояние, если готово. Есть отмена по handle и автоматическая отмена при уничтожении подписчика. Для UI предусмотрена Blueprint-подписка с Ready и Invalidated.
- Unpossess, respawn, смена PlayerState и EndPlay инвалидируют прежний контекст до новой готовности. Запоздалые callbacks проверяют поколение и текущий Pawn. Повторное уведомление в одном поколении не повторяет bind/grant/init.
- Триггеры событийные: BeginPlay, possession/OnRep, InitAbilityActorInfo и доступность компонентов/данных. Без постоянного Tick, сканирования всех акторов и реплицируемого универсального bReady.
- Наличие inventory component, получение начальных item subobjects и возможность показать пустой инвентарь — разные условия. Не использовать Items.Num()>0 как готовность. Для начального снимка сначала определить реальную потребность UI; при необходимости отдельная ревизия и проверка разрешения ссылок, а не предположение о порядке репликации.

## Границы зависимостей

Использовать AActor для позиции/authority, APawn для possession/контроля, ACharacter для movement/mesh, IAbilitySystemInterface для ASC, компонент для combat/interaction/aim. Небольшой интерфейс жизненного состояния допустим там, где нужны death и проверка актуальности Avatar; не создавать большой интерфейс со всеми методами Character.

ALS mantle, ragdoll, overlay и held-object presentation остаются в адаптерах, где зависимость от ALS оправдана. PlayerState продолжает владеть ASC, здоровьем и inventory. Readiness не заменяет авторитетные проверки RPC, damage и LifeSerial.

## Пакеты реализации

1. **Lifecycle/готовность.** Ввести context/subscriptions и lifecycle hooks. Перевести одного потребителя UI на Ready/Invalidated; сохранить существующую GAS-инициализацию до доказанной эквивалентности. Результат: нет таймера ожидания/повторных подписок у переведённого потребителя, доступна причина неготовности.
2. **Input и конфигурация способностей.** Создать InputConfig и Pawn input component, назначить текущие IA/IMC в assets. Удалить runtime MapKey/NewObject input actions и action-specific методы Controller. Перенести автоогонь, UI-запросы и drop RPC к существующим владельцам/компонентам, тестовый harness — в отдельный тестовый компонент. Удалить C++ fallback выдачи после заполнения Ability Set. Учесть порядок ALS bindings и снять дубли Jump/Aim.
3. **Снижение связности.** Перевести сначала Aim/UI/projectile и общие abilities на базовые классы, ASC и components; затем Combat/Interaction. Отделить ALS presentation adapter. Не переименовывать весь проект и не менять hierarchy ALS Controller без отдельной необходимости.
4. **Миграция и завершение.** Назначить configs в существующих Blueprint, сохранить графы. После проверки ссылок удалить временные compatibility wrappers. Коротко обновить документацию владельцев и инструкцию добавления способности.

Каждый пакет — отдельный обозримый diff и одна сборка после статического просмотра; повторная сборка только при ошибках/новых необходимых C++ изменениях. Не держать несколько конкурирующих реализаций включёнными одновременно. Для редакторской миграции согласовать окно закрытого редактора.

## Проверки, требующие отдельного апрува

После согласованного пакета: сервер + два клиента; перестановки possession/OnRep; respawn и старые callbacks; held input при UI/death/unpossess; отсутствие двойной активации/выдачи; пустой inventory и поздние subobjects; remote proxy без Controller; сохранение server fire limiter и защиты от попадания в старый Pawn. Travel — только если включён в согласованный объём.

## Вне scope

Новая FSM персонажа, изменение AnimBP/ALS plugin, инвентарь с нуля, новые способности/оружие, extraction loop, общий framework загрузки любых ассетов, перенос сторонних подсистем целиком. Для действий пока достаточно GAS tags/cancel/block и существующих ALS movement states. Отдельная FSM обсуждается только при конкретной последовательности, которую эти механизмы не выражают.

Первым реализуется пакет 1. Этот документ не является разрешением на тестирование.
