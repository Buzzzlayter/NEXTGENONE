# TODO: качество сетевой стрельбы

Цель — отзывчивая серверная стрельба для extraction shooter с физическими пулями.
Это порядок следующих работ, а не подтверждение готовности. Сборку выполняет
пользователь; игровые и сетевые проверки требуют отдельного разрешения.

## Сохраняем основу

- Сервер решает, разрешён ли выстрел, создаёт снаряды, расходует патроны и наносит урон через GAS.
- Клиент сообщает намерение стрелять и параметры взгляда, но не подтверждает попадание.
- Темп ограничен серверным cooldown на PlayerState ASC; повторная активация и переэкипировка не сбрасывают ограничение.
- GA_PrimaryAttack управляет удержанием, ServerOnly GA_Fire выполняет отдельный выстрел.
- Gameplay input передаёт теги в GAS, не вызывает Combat/Inventory.
- Косметика не меняет урон и патроны. Проверки текущего Avatar и актуальности оружия сохраняются.

## 1. Подтвердить серверный темп

- [ ] Пользователь собирает последнюю реализацию. Проверить override GA_PrimaryAttack: Local Predicted; GA_Fire: Server Only.
- [ ] После разрешения измерить интервалы реальных серверных выстрелов игрока и бота; сопоставить с FireInterval и серверным FPS.
- [ ] Проверить автомат/полуавтомат, отпускание до первого TargetData, окончание патронов, потерю ADS, UI-блокировку, reload, смену оружия, смерть и respawn.
- [ ] Убедиться, что частые press/release, TargetData и переэкипировка не ускоряют стрельбу.

Критерий: одна серверная временная шкала выстрелов, без зависания очереди и выстрелов старой активации. Серверные задержки не создают неограниченный догоняющий залп.

## 2. Локальный отклик и согласование косметики

- [ ] Сразу на owning client показывать выстрел: звук, вспышку и отдачу.
- [ ] Ввести идентификацию предсказанного выстрела и сопоставление с серверным результатом; не считать локальный номер доверенным доказательством выстрела.
- [ ] Серверное событие не должно повторно проигрывать уже показанную косметику владельцу.
- [ ] Определить поведение при отказе сервера: косметический выстрел не создаёт урон и не закрепляет неверное количество патронов.

Критерий: отклик не ждёт сетевого round trip; у наблюдателей и владельца нет двойных эффектов. LocalPredicted у способности сам по себе этого не обеспечивает.

## 3. Доставка прицеливания

- [ ] Измерить текущие TargetData: обновление каждые 50 мс, прекращение очереди через 250 мс без новых данных на сервере.
- [ ] Проверить запаздывание направления при быстром ведении цели и возможные отказы из-за различия с серверным ControlRotation.
- [ ] По результатам решить, нужен ли отдельный unreliable-поток последнего взгляда с порядковым номером. Start/stop, смена активации и устаревшие пакеты должны иметь однозначную обработку.
- [ ] Ограничить частоту обработки входящих данных на сервере; клиентский поток не определяет темп выстрелов.
- [ ] Сохранить проверки конечности чисел, допустимого origin, направления, препятствий, текущего Avatar и ревизии экипировки.

Критерий: потери пакетов не заставляют сервер воспроизводить очередь старых направлений; запоздалые данные не возобновляют остановленную стрельбу.

## 4. Попадания и обратная связь

- [ ] Зафиксировать серверную collision-модель: капсула, hit zones или skeletal bodies; отдельно определить голову, тело и броню.
- [ ] Проверить быстрые снаряды на тонких препятствиях и при низком серверном FPS; настраивать sweep/substepping по результату.
- [ ] Подтверждение попадания, урона и убийства отправлять стрелку только после серверного расчёта. Не выводить hit marker из локального трассера.
- [ ] Согласовать muzzle obstruction, третье лицо, направление импакта и поверхность эффекта.
- [ ] Решить судьбу уже выпущенной пули после смерти/respawn стрелка. Защита новой жизни не должна случайно запрещать согласованные взаимные убийства.

Критерий: визуальное попадание и серверный результат объяснимы одной моделью; старый труп не получает урон за новую жизнь.

## 5. Задержка и стоимость

- [ ] После отдельного разрешения проверить dedicated server + два клиента: разные RTT, jitter, packet loss и серверный FPS. Пределы приемлемости согласовать до прогона.
- [ ] Измерить CPU, сетевой трафик и число Actor при нужном количестве стрелков и снарядов.
- [ ] При подтверждённой стоимости сравнить текущие реплицируемые снаряды с серверной симуляцией и локальными косметическими трассерами.
- [ ] Отдельно выбрать политику компенсации задержки для баллистики: момент запуска, время полёта, движение цели, максимальная уступка стрелку. Не переносить hitscan rewind без адаптации.

Критерий: измеренный бюджет и согласованная честность попаданий. Pooling, rewind и смена транспорта вводятся под установленную проблему.
